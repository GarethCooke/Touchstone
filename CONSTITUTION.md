## §1 Purpose and reader

The programme is one built thing and its explanatory layer: **Touchstone**, a C++20
pricing-and-risk library, and **learn.garethcooke.com**, a tutorial for developers who work
alongside quants. The tutorial's checks are the library's tests; the demos run on it.

Organising thesis: linear products (forwards, futures, swaps) are priced by discounting and
no-arbitrage; only nonlinear payoffs (options) need stochastic calculus.

Register: bounded claims. A page's job is not to impress; it is to let an experienced reader
tell within thirty seconds that nothing is claimed beyond what is demonstrated.

## §2 Truth invariants

- **I1 — Nothing published that isn't demonstrated.** Every quantitative claim on a page
  MUST map to a test, a committed experiment result, or a cited source.
- **I2 — The owner writes the maths.** Part 2 prose is the owner's, in their own words.
  Sessions convert, format, extract snippets and draft checks; they MUST NOT author Part 2
  prose. Sessions MAY draft Part 0, 1 and 3 prose only where a milestone says so, marked for
  owner review and never published unreviewed.
- **I3 — No prose-only code.** Every snippet shown MUST be extracted from a file that runs
  in CI.
- **I4 — QuantLib is the oracle, never a dependency.** Reference values are generated by
  QuantLib-Python, committed as versioned JSON with the QuantLib version recorded. Touchstone
  MUST NOT link QuantLib.
- **I5 — Every page has a check that fails on misunderstanding.** Every wrong option MUST
  name the misconception it encodes, and the feedback MUST say why it is wrong.
- **I6 — Determinism.** Same seed, same result: numpy experiments seeded explicitly;
  TypeScript demos and C++ on the shared RNG of `docs/rng.md`. Agreement is to stated
  tolerances, never bit-exact.
- **I7 — Market data are dated fixtures.** Committed to the repo with source and date in the
  filename; no live fetches in v1; redistribution terms checked before a snapshot is
  committed.
- **I8 — No accounts, no backend, no PII.** Progress lives in localStorage. Analytics is
  Umami and nothing else.

## §3 Publication invariants

- **I9 — Status model.** Every page is `tbc`, `draft` or `published`. Production builds emit
  `published` only; preview builds also emit `draft`; `tbc` is never a route.
- **I10 — No wall of TBC.** The production index shows the curriculum tree only when at
  least one page is `published`; otherwise it shows the holding page.
- **I11 — The portal follows reality.** The portfolio links the tutorial only once Part 2
  has published pages, and carries a Touchstone card only once T5 has passed its tollgate.
  Portal changes happen only through a portal brief executed in the portfolio repo.
- **I12 — Public follows readiness.** `touchstone` is public from T0 under MIT: a library
  in progress is a normal public state, and public repos get unlimited CI minutes.
  `touchstone-learn` is private until L6: a tutorial in progress is not a normal public
  state. At L6 it goes public under CC BY 4.0 for prose and MIT for code, unless amended.
- **I13 — Copy is the owner's.** Sessions MUST NOT invent site copy. Placeholder text is
  labelled as placeholder and never reaches production.

## §4 Architecture invariants

- **I14 — `curriculum.ts` is the single source of truth** for structure, order and status.
  MDX carries prose only; checks live beside their page.
- **I15 — Demos are separated from compute by `PricingBackend`.** TypeScript implementation
  first; WASM implementation swapped in behind the same interface. Both MUST pass the same
  known-answer and parity tests.
- **I16 — The RNG is frozen** by `docs/rng.md` (xoshiro128\*\*, fmix32 seed expansion,
  53-bit doubles, AS241 normals, known-answer fixtures). Changing it is an amendment and
  invalidates every fixture.
- **I17 — Vendoring runs one way.** Touchstone → learn site (WASM artifact, golden JSON,
  experiment results), pinned by release tag or commit. Never the reverse. No submodules.
- **I18 — Repo boundaries.** Learn-site sessions edit only `touchstone-learn`; library
  sessions edit only `touchstone`. Crucible and the portfolio are read-only source material.
- **I19 — The stack is fixed.** Site: Next on Crucible's version line, MDX, KaTeX, Shiki,
  D3 plus canvas, Tailwind v4 with tokens copied from the portfolio, vitest, Amplify, Node 22.
  Library: C++20, CMake, GCC and Clang, Emscripten, GitHub Actions. Experiments: Python
  3.12+, numpy, scipy, uv. Additions are amendments.
- **I20 — Correctness is three-way agreement.** Closed form, Monte Carlo and finite
  differences MUST agree within stated tolerances; analytic and bump Greeks likewise; Monte
  Carlo standard error is reported, never hidden.
- **I21 — v1 scope is fixed.** European vanillas, one underlying, constant rate and
  volatility, dividend yield. Anything else is Part 4 and enters only by amendment.

## §5 Session protocol

- **P1 — Read first, always:** this constitution, `ROADMAP.md`, the current milestone, the
  previous milestone's log entry. Then `node_modules/next/dist/docs/` before any Next API.
- **P2 — One milestone per session.** A session MUST NOT begin the next milestone. If the
  exit criteria are met early, stop and log.
- **P3 — The session writes its own work order** at the top of its log entry: goal, steps,
  decisions. Work orders derive from the roadmap; the owner does not supply briefs. Exception:
  L0 uses `docs/briefs/S0-learn-site-scaffold.md`, already written.
- **P4 — Decisions.** Where the constitution and milestone are silent, the session MAY ask
  the owner in-session. If the owner is absent it picks the reversible option, records
  "Decision — owner may overrule", and continues. It MUST stop for irreversible or
  public-facing choices: anything reaching production, licences, hostnames, repo visibility,
  spending money.
- **P5 — Evidence pack** at the end of every milestone, under `docs/evidence/<milestone>/`
  in the executing repo: `summary.md` (one page: exit criteria as a checklist with pass/fail,
  what changed and why, links), `build.txt`, `tests.txt`, `screenshots/` for UI in light and
  dark, `diff.txt` (`git diff --stat` against the milestone's base).
- **P6 — Git.** Work on branch `m/<milestone-id>`; commit freely; push the branch; never push
  to `master`. The owner merges after the tollgate.
- **P7 — Log format**, written at the top of `docs/evidence/<milestone>/summary.md` in the
  executing repo — never in `ROADMAP.md`, which lives in `touchstone` and is edited only by
  the owner (I18): `### YYYY-MM-DD · model · one-line summary` then **Done**, **Decisions
  (with why)**, **Not done**, **Exact next step**. At merge the owner ticks the milestone in
  `ROADMAP.md` and adds a one-line pointer to the evidence pack.
- **P8 — Model routing.** Opus (Cowork orchestrating Claude Code) executes milestones.
  Sonnet MAY execute milestones marked *mechanical*. Fable runs Fable-review tollgates and
  the teaching sessions, and MUST NOT execute implementation milestones.

## §6 Tollgate protocol

Two kinds. **Self-verified (V):** the executing session proves the exit criteria in the
evidence pack; the owner merges. **Fable review (F):** a fresh Fable session in the owner's
Claude Project receives the prompt below and the evidence pack. Which milestones are F is
fixed in `ROADMAP.md`.

Tollgate prompt, verbatim, nothing added:

> Tollgate `<milestone-id>`. Read `CONSTITUTION.md`, the `<milestone-id>` section of
> `ROADMAP.md`, and `docs/evidence/<milestone-id>/summary.md`; open other evidence only if a
> criterion needs it. Return: **Verdict** (PASS / PASS WITH DEFECTS / FAIL); **Defects**, each
> against an invariant id or exit criterion, with severity and fix; **Amendments** proposed,
> if any; **Unlocks** — the next milestone's first step.

A tollgate session reads only what the prompt names; it MUST NOT re-read the codebase unless
a defect requires it. In a chat tollgate the owner uploads the evidence files or connects the
repo. The owner saves the verdict as `docs/evidence/<milestone>/verdict.md`. FAIL returns
the milestone to the executor with the defect list as its work order.

## §7 Teaching track

Sessions S1–S11 map to pages 2.1–2.11, one fresh Fable session per topic. Inputs: the page's
summary and check from `docs/index-v1.md`, and whatever the owner brings. Outputs, committed
by the owner: a numpy experiment script and its JSON result in `touchstone/experiments/`;
the owner's draft page in `touchstone-learn/drafts/2.x.md`; draft check questions, written
by Fable for the owner's approval. Fable reviews the draft against I1 before it is committed.
Drafts enter the site as `draft` at milestone L2.
