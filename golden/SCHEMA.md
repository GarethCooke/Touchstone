# `bs_vanilla.json` — schema, units and tolerances

Reference prices and Greeks for European vanilla options under Black–Scholes–Merton,
generated by [`generate_bs_vanilla.py`](generate_bs_vanilla.py) from QuantLib and read by
Touchstone's C++ tests. QuantLib is the oracle and never a dependency (`CONSTITUTION.md`
I4): this file is what the dependency is replaced by.

Schema id `touchstone/golden/bs_vanilla@1`. A change to the meaning of any field, or to the
units below, is a new schema id — not an edit to this one.

## Document structure

```
{
  "schema", "generator", "documentation", "model",
  "oracle":      { library, version, binding, engine, day_count, calendar, evaluation_date },
  "conventions": { one line per field, stating its units },
  "tolerances":  { cases, edge_cases, note },
  "axes":        { the values each grid axis takes },
  "fields":      [ the keys every case carries ],
  "counts":      { cases, edge_cases, total },
  "cases":       [ 7200 rows — the main grid ],
  "edge_cases":  [ 34 rows — near-degenerate corners, each with a "label" ]
}
```

Cases are written one per line so that `git diff` names the rows that moved rather than
reporting one changed line of two megabytes.

**`oracle.version` is the whole point of the file.** Reference values are only meaningful
alongside what produced them. If the version changes, the numbers may change, and the diff is
the record of it.

## Fields

Every case in `cases` carries all fifteen. Every case in `edge_cases` carries those plus
`label`.

### Inputs

| Field | Type | Meaning |
|---|---|---|
| `type` | `"call"` \| `"put"` | Option type. |
| `spot` | float | Spot price of the underlying, `S`. |
| `strike` | float | Strike, `K`. |
| `vol` | float | Volatility `σ`, annualised, as a decimal — `0.30` is 30%. |
| `rate` | float | Continuously compounded risk-free rate `r`, as a decimal. May be negative. |
| `dividend_yield` | float | Continuous dividend yield `q`, as a decimal. |
| `expiry_days` | int | Days from the evaluation date to expiry. |
| `expiry_years` | float | Year fraction `T`. Exactly `expiry_days / 365` — Actual/365 Fixed with whole-day expiries, so nothing rounds between the grid and the number. |

### Outputs

All seven are **raw partial derivatives**, exactly as QuantLib returned them. No market
scaling is applied anywhere in the pipeline.

| Field | Definition | Units |
|---|---|---|
| `price` | `V` | Currency, same units as `spot` and `strike`. |
| `delta` | `∂V/∂S` | Per 1.00 of spot. |
| `gamma` | `∂²V/∂S²` | Per 1.00 of spot, squared. |
| `vega` | `∂V/∂σ` | **Per 1.00 of volatility**, not per volatility point. Divide by 100 for the per-point figure a desk quotes. |
| `theta` | `∂V/∂t` | **Per year**, not per day. Negative for a long position that decays. Divide by 365 for a per-day figure. |
| `rho` | `∂V/∂r` | **Per 1.00 of rate**, not per basis point. |
| `dividend_rho` | `∂V/∂q` | Per 1.00 of dividend yield. |

Why raw: a per-day theta or a per-point vega puts a convention factor inside the oracle,
where an arithmetic identity belongs. It would then have to be applied identically in three
places — the generator, the C++ tests, the TypeScript demo — and a test could fail because
two of them disagreed about 365 versus 365.25, which says nothing about whether
Black–Scholes was implemented correctly. Scale at the point of display, once, visibly.

## The formulas

With `φ` the standard normal density and `N` its distribution function, `w = +1` for a call
and `−1` for a put:

```
d₁ = [ ln(S/K) + (r − q + σ²/2)·T ] / (σ√T)
d₂ = d₁ − σ√T

price        = w · [ S·e^(−qT)·N(w·d₁) − K·e^(−rT)·N(w·d₂) ]
delta        = w · e^(−qT)·N(w·d₁)
gamma        = e^(−qT)·φ(d₁) / (S·σ√T)
vega         = S·e^(−qT)·φ(d₁)·√T
theta        = −S·e^(−qT)·φ(d₁)·σ / (2√T) − w·r·K·e^(−rT)·N(w·d₂) + w·q·S·e^(−qT)·N(w·d₁)
rho          = w · K·T·e^(−rT)·N(w·d₂)
dividend_rho = −w · T·S·e^(−qT)·N(w·d₁)
```

`N(x) = ½·erfc(−x/√2)`, which is the route `std::erfc` gives the C++ (tech-decision B3) and
the one [`verify_bs_vanilla.py`](verify_bs_vanilla.py) uses to re-derive every row
independently. Computing `N(−x)` as `1 − N(x)` loses the left tail entirely and will not
reproduce this file.

## The grid

`cases` is the full cartesian product of the seven axes — 5 × 5 × 4 × 3 × 3 × 4 × 2 = 7200
rows.

| Axis | Values |
|---|---|
| `spot` | 60, 80, 100, 120, 150 |
| `strike` | 80, 90, 100, 110, 120 |
| `vol` | 0.05, 0.15, 0.30, 0.60 |
| `rate` | −0.005, 0.01, 0.05 |
| `dividend_yield` | 0.00, 0.02, 0.05 |
| `expiry_days` | 91, 365, 730, 1826 (≈ 3m, 1y, 2y, 5y) |
| `type` | call, put |

Spot and strike are separate axes rather than a single moneyness axis, so the file exercises
absolute scale as well as moneyness. Moneyness runs from 0.5 to 1.875. A negative rate is in
the main grid rather than the edge block because it is a normal market state, not a corner.

The product does mean part of the grid is far out of the money and numerically dead. That is
coverage, not waste — a correct implementation must return a very small number there rather
than a NaN — but it changes how the rows should be compared. Measured on the committed file:

| Price band | Rows | Share |
|---|---|---|
| ≥ 1 | 5571 | 77.4% |
| 10⁻³ … 1 | 880 | 12.2% |
| 10⁻⁸ … 10⁻³ | 341 | 4.7% |
| 10⁻¹⁵ … 10⁻⁸ | 136 | 1.9% |
| < 10⁻¹⁵ | 272 | 3.8% |

## The edge block

`edge_cases` holds 17 labelled parameter sets, each as a call and a put. They are kept out of
the main grid because they are where a correct closed form and a correct oracle can still
disagree in the last few digits, and because a test should be able to say *these are the hard
ones* rather than discovering it from a failure.

`one-day-atm`, `one-day-deep-itm-call`, `one-day-deep-otm-call`, `near-zero-vol-atm`,
`near-zero-vol-itm-call`, `near-zero-vol-otm-call`, `very-high-vol-atm`, `very-high-vol-long`,
`deep-itm-call-1y`, `deep-otm-call-1y`, `zero-rate-zero-yield`, `rate-equals-yield`,
`negative-rate-long`, `high-yield-over-rate`, `ten-year-atm`, `tiny-spot`, `large-spot`.

They are not limits. `σ → 0` and `T → 0` are exact limits with closed-form answers, and
T1 tests them directly rather than against this file.

## Precision

Read this before writing a comparison. Two properties of the oracle matter, both measured on
the committed file rather than assumed.

### Compare absolutely below 1.0, relatively above it

Deep out-of-the-money prices are the residue of subtracting two numbers of order `S`, so
their absolute accuracy is a few ulps of `S` — about 10⁻¹⁴ here — regardless of how small the
true value is. **106 rows carry a slightly negative price**, the most negative being
−1.7 × 10⁻¹⁴, where the true value is a positive number around 10⁻¹⁹. These are not errors in
the file and must not be clamped: they are what the oracle returned, and a correct C++
implementation may legitimately land on the other side of zero.

The consequence: a relative comparison is meaningless below the noise floor. Use

```
scale = max(|reference|, 1.0)
pass  = |actual − reference| / scale  ≤  tolerance
```

which is relative for material values and absolute for the rest. The same rule applies to
every Greek: `vega` falls to 10⁻¹⁷³ on deep in-the-money rows whose price is well above 1.

### Theta is less accurate at short expiries, by a known factor

QuantLib derives theta by a route that divides by the year fraction, so its absolute error
grows as `1/T`. Measured across every expiry in the file, against an independent evaluation:

| `expiry_days` | worst \|Δθ\| / S | × T |
|---|---|---|
| 1 | 1.5 × 10⁻¹³ | 4.2 × 10⁻¹⁶ |
| 91 | 1.1 × 10⁻¹⁵ | 2.6 × 10⁻¹⁶ |
| 365 | 3.4 × 10⁻¹⁶ | 3.4 × 10⁻¹⁶ |
| 730 | 1.4 × 10⁻¹⁶ | 2.8 × 10⁻¹⁶ |
| 1826 | 5.2 × 10⁻¹⁷ | 2.6 × 10⁻¹⁶ |
| 3652 | 1.3 × 10⁻¹⁷ | 1.3 × 10⁻¹⁶ |

The last column is constant at one to two ulps: the error is `S·ε/T` exactly. So the golden
theta on a one-day option is good to about 10⁻¹¹ absolute, not 10⁻¹⁵ — comfortably inside the
edge block's 10⁻⁸ but only one order of magnitude inside the main grid's 10⁻¹⁰. The main grid's
shortest expiry is 91 days, where the effect is negligible; the one-day rows live in the edge
block partly for this reason.

A C++ implementation computing theta directly from the closed form will be *more* accurate
than this file at short expiries. That is expected. Do not tighten the tolerance to chase it.

### Tolerances

| Block | Tolerance | Rationale |
|---|---|---|
| `cases` | 10⁻¹⁰ | Roadmap T1's stated figure. Comfortable: the observed spread between two independent implementations is a few ulps of natural scale. |
| `edge_cases` | 10⁻⁸ | Looser by construction, not by concession — short expiries amplify theta, and near-zero vol collapses gamma and vega toward zero where the last digits stop meaning anything. |

Both are carried in the file's `tolerances` block so a test reads them rather than hard-codes
them.

## Regenerating

```bash
uv sync
uv run golden/generate_bs_vanilla.py     # rewrites bs_vanilla.json
uv run golden/verify_bs_vanilla.py       # independent cross-check, exit 0 on pass
```

The generator is deterministic: the evaluation date is fixed in source rather than taken from
the clock, no timestamp is written into the output, and floats are serialised at shortest
round-trip precision. Same QuantLib version, same bytes — verified by regenerating twice and
comparing SHA-256. If the regenerated file differs from the committed one, either QuantLib
changed or the grid did, and `git diff` says which.

`verify_bs_vanilla.py` is the check that the file is worth trusting. It re-derives all seven
values for all 7234 rows from the formulas above, checks put–call parity on all 3617 matched
pairs, asserts the sign and unit conventions this document claims, and confirms the document's
own structure. It exists because a generator that drives QuantLib wrongly — dividend handle
where the rate handle belongs, an accessor that means something other than what is written
here — produces a perfectly self-consistent file full of wrong numbers, and nothing else in
the pipeline would notice.
