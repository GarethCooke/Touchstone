2. Why the refusals are repeated: the two ways the module dies
-------------------------------------------------------------

  An exception that unwinds WebAssembly frames — C++ or JavaScript — does not restore the
  module's stack pointer. Embind restores it only around calls that stack-allocate their
  arguments, and these take emscripten::val. Each such throw leaks the frames' stack, and
  the default 64 KB stack runs out. Measured at 9d64a8c and again on the final tree
  (7c1be27), with the same counts:

  a. A JavaScript exception thrown inside a call. The binding's first design read argument
     fields with val property access, so a getter that throws would throw from inside the
     module. Driving the hidden raw_ function directly, which skips errors.post.js's
     structured clone, reproduces that:

         call 2074: RuntimeError: memory access out of bounds

     The first design also raised the C++ exception's JavaScript error from inside the
     module (an EM_JS throw); its probe failed the same way before reaching 200,000. Both
     were replaced by the design in binding.cpp: the error is returned, and thrown by
     errors.post.js after the call has returned; the arguments are cloned before it.

  b. Without exception catching (build-wasm-noexcept). The first refusal is
     'RuntimeError: Aborted(undefined)' — the library's message lost — and the abort is
     itself a JavaScript throw through the module's frames:

         refusal 178: RuntimeError: table index is out of bounds

  The smoke test's 100,000 of each kind is 48 times (a) and 560 times (b).

  The two probes, as run (scratch files, not committed):
